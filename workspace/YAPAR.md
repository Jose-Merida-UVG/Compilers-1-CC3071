# YAPar — Parser Generator

A Go-based SLR(1) parser generator. You write a `.yalp` spec file declaring
your tokens and grammar; the tool computes FIRST/FOLLOW sets, builds the LR(0)
automaton, and generates SLR(1) parse tables. Always paired with a `.yal` lexer
spec file of the same name.

---

## File Structure

A `.yalp` file has two sections separated by `%%`:

```
/* comment */

%token TOKEN_A
%token TOKEN_B TOKEN_C
IGNORE WS

%%

nonterminal:
    nonterminal TOKEN_A other
  | other
;

other:
    TOKEN_B
  | /* empty */
;
```

### Token declarations

```
%token NAME
%token NAME_A NAME_B NAME_C
```

Declares terminals the parser knows about. Each name gets a unique integer ID
(1-based, in declaration order). These constants are generated and injected into
the combined lexer+parser output — do **not** define them yourself in the `.yal`
header.

Multiple names on one `%token` line are allowed.

### IGNORE

```
IGNORE WS
IGNORE COMMENT NEWLINE
```

Tells the parser that these tokens exist in the lexer but will never reach the
parser (the lexer skips them). A token listed under `IGNORE` must not appear in
any production rule — the parser would never see it, making any such rule
unreachable. This is a hard error at build time.

### Productions

```
nonterminal:
    body1
  | body2
;
```

- Non-terminals are lowercase identifiers.
- Terminals are uppercase (must be declared with `%token`).
- Empty productions: `| /* empty */`
- Each rule ends with `;`
- The first non-terminal declared is the start symbol.

## Pairing with a `.yal` file

Every `.yalp` must be paired with a `.yal` of the same base name:

```
specs/arithmetic.yal   ←  lexer patterns + actions
specs/arithmetic.yalp  ←  tokens + grammar
```

The generator reads both files and produces a combined lexer+parser program.

### Lexer File Requirements

The `.yal` file must follow specific rules to work with the parser:

1. **Do NOT define token constants in the header**
   ```
   {
       // ✗ WRONG - parser generator will inject these
       const (
           INT = 1
           PLUS = 2
       )
   }
   ```

   Token constants are **generated by YAPar** from the `%token` declarations in
   the `.yalp` file. The combined output includes these automatically.

2. **Token actions must return the token name**
   ```
   rule gettoken =
     int    { return INT }     // ✓ Correct - returns token name
   | '+'    { return PLUS }
   | ws+    {  }               // ✓ Correct - skips whitespace, no return
   ```

3. **Ignored tokens should not return**
   ```
   // In .yalp:
   IGNORE WS

   // In .yal:
   rule gettoken =
     ws+  {  }                 // ✓ No return - parser will never see it
   ```

4. **Use standard EOF and ERROR handling**
   - `EOF` (value 0) is automatically available
   - `ERROR` (value -1) is automatically available
   - Don't define these yourself

5. **Print statements in lexer actions**
   ```
   rule gettoken =
     int  { fmt.Print("INT    "); return INT }
   ```
   These prints appear during tokenization, useful for debugging but should be
   removed in production parsers.

## Input Constraints

- **ASCII only.** Both files are rejected before processing if any non-ASCII
  byte is found.
- **Comments** use C-style block syntax: `/* ... */`. Single-line `//` is not
  supported.
- Terminals **must** be uppercase, non-terminals **must** be lowercase.

---

## What the tool produces

Building a `.yalp` generates files under `workspace/programs/<name>/`:

| File | Contents |
|------|----------|
| `lexer.go` | Generated lexer with token constants injected |
| `parser.go` | Generated parser with ACTION/GOTO tables, `Parse()` function, and `main()` |
| `docs/dfa.json` | DFA graph for the visualizer tab |
| `docs/lr0.json` | LR(0) automaton for the visualizer tab |
| `docs/slr.json` | SLR(1) table for the visualizer tab |

The generated program is complete and runnable:
```bash
cd workspace/programs/arithmetic
go run lexer.go parser.go ../../input/test.arithmetic
```

## Parser Output Format

When you run a generated parser against input, it produces:

### 1. Parse Actions
Shows the shift/reduce sequence:
```
── Parse Actions ──
Shift:  INT
Reduce: atom → INT
Reduce: power → atom
Reduce: term → power
Shift:  PLUS
Shift:  INT
...
```

Each `Shift` pushes a terminal onto the stack.
Each `Reduce` applies a production rule, replacing the body with the head.

### 2. Symbol Table
Chronologically ordered list of all tokens encountered:
```
── Symbol Table ──
LEXEME               TOKEN                LINE:COL
2                    INT                  1:1
+                    PLUS                 1:3
3                    INT                  1:5
```

Shows:
- **LEXEME**: The actual text matched
- **TOKEN**: The token name (not ID number)
- **LINE:COL**: Position in the input (1-indexed)

### 3. Result
- `OK — input accepted by the grammar.` if successful
- `syntax error: unexpected TOKEN at line X, col Y` if parse fails
- `lexical error: unrecognized input 'X' at line Y, col Z` if lexer fails

## Visualizer tabs

After clicking **◎ Build Parser** three tabs open automatically:

- **SLR table** — Action and Goto tables, FIRST/FOLLOW sets, production list,
  and any shift/reduce or reduce/reduce conflicts.
- **LR(0) graph** — the full automaton with item sets and transitions.
- **DFA** — the lexer DFA for the paired `.yal`.

## SLR(1) constraints

The grammar must be SLR(1). Common sources of conflicts:

**Shift/reduce** — ambiguous operator associativity. Fix with left recursion for
left-associative operators:
```
expr: expr PLUS term | term   ← left-recursive, unambiguous
```

**Dangling else** — `if cond stmt` followed by `else` is a classic conflict.
Fix by requiring braces, or by always requiring the `else` branch.

**Reduce/reduce** — two productions apply for the same lookahead. Usually
signals an ambiguous grammar. Restructure so each lookahead leads to at most
one reduce action.

Conflicts are reported in the SLR visualizer tab and do not block the build,
but the generated parser will behave unpredictably in conflicting states.

## Type-Safe Grammars

You can enforce type safety at the grammar level by using separate non-terminals
for different types:

```
%token INT FLOAT KWTRUE KWFALSE
%token PLUS MINUS TIMES DIV
%token AND OR NOT
%token LT GT EQ

%%

stmt:
    IDENT ASSN numexpr SEMI      // numeric assignment
  | IDENT ASSN boolexpr SEMI     // boolean assignment
  | KWIF boolexpr block          // condition must be boolean
;

numexpr:
    numexpr PLUS numterm
  | numexpr MINUS numterm
  | numterm
;

numterm:
    numterm TIMES numprimary
  | numterm DIV numprimary
  | numprimary
;

numprimary:
    INT | FLOAT | IDENT
  | LPAREN numexpr RPAREN
;

boolexpr:
    boolexpr OR boolterm
  | boolterm
;

boolterm:
    boolterm AND boolfactor
  | boolfactor
;

boolfactor:
    NOT boolfactor
  | boolprimary
;

boolprimary:
    KWTRUE | KWFALSE | IDENT
  | numexpr LT numexpr           // comparison produces boolean
  | numexpr GT numexpr
  | numexpr EQ numexpr
  | LPAREN boolexpr RPAREN
;
```

This makes `5 + true` a **parse error** instead of just a semantic error.

**Limitation:** Variables (IDENT) can appear in both contexts since the parser
doesn't track variable types. Runtime checks are still needed for variable type
misuse.

## Example: arithmetic.yalp

```
%token FLOAT INT
%token POW KWPOW
%token PLUS MINUS TIMES DIV MOD
%token LPAREN RPAREN COMMA
%token IDENT

%%

expr:
    expr PLUS term
  | expr MINUS term
  | term
;

term:
    term TIMES power
  | term DIV power
  | term MOD power
  | power
;

power:
    atom POW power
  | atom
;

atom:
    INT
  | FLOAT
  | IDENT
  | LPAREN expr RPAREN
  | KWPOW LPAREN expr COMMA expr RPAREN
  | IDENT LPAREN args RPAREN
;

args:
    arglist
  | /* empty */
;

arglist:
    expr
  | arglist COMMA expr
;
```

## How to Use

### 1. Write your specs

Create `specs/<name>.yal` and `specs/<name>.yalp` with the same base name.

The `.yal` file should:
- **NOT** define token constants (YAPar generates these)
- Have token actions that `return TOKEN_NAME`
- Skip ignored tokens by not returning

### 2. Build

Open the `.yalp` in the editor and click **◎ Build Parser**. The tool reads
both files, generates token constants, compiles the lexer and parser together,
and opens the visualizer tabs.

### 3. Run against input

Create a test file in `workspace/input/` with an extension matching the spec
name (e.g. `test.arithmetic` → uses `arithmetic.yal` + `arithmetic.yalp`).
Open it and click **▶ Run**. Output appears in the terminal and is saved to
`workspace/output/<filename>.out`.

### 4. View parse trace

The output shows:
- All parse actions (shift/reduce sequence)
- Symbol table (tokens in order encountered)
- Success or error message with line/column

## Common Issues

### Token constant conflicts
```
Error: redeclared in this block
```
**Fix:** Remove token constant definitions from `.yal` header. YAPar generates these.

### Token not returned by lexer
```
Warning: token FOO declared in .yalp but never returned by lexer
```
**Fix:** Add `return FOO` to the appropriate lexer action, or remove the token
from the `.yalp` %token declarations.

### IGNORE token used in grammar
```
Error: token WS is IGNORE but used in production "stmt"
```
**Fix:** Remove the ignored token from the production rules. The parser never
sees ignored tokens.

### Shift/reduce or reduce/reduce conflict
Check the SLR visualizer tab for details. Usually requires grammar restructuring
to eliminate ambiguity.

---

## Advanced: Separate Lexer and Parser

While YAPar generates a combined lexer+parser program, you can still build them
separately for testing:

1. **Lexer only:** Use the DFA visualizer tab to test tokenization
2. **Parser only:** Not supported standalone - requires lexer integration

The combined output in `programs/<name>/` is the recommended approach.
